# TVBox 配置兼容性说明

本客户端把一份 **TVBox 接口（配置）JSON** 作为数据入口。TVBox 生态的配置由社区手写、质量参差不齐，
而且**大量依赖客户端自身的 Spider 引擎**——这部分纯 JS/Electron 客户端永远跑不了。
本文说明「哪些能用、哪些会被跳过、为什么」，便于你判断一份配置值不值得用。

> 字段语义的逐条考证（含上游客户端源码出处与验证状态）见
> [TVBox 配置规范](tvbox-config-and-ui-spec.md)。

## 能直接使用

| 配置内容 | 说明 |
| --- | --- |
| `sites[]` 中 `type:1` / `type:2` | JSON 采集站（Apple CMS 协议）：可搜索、可播放。**按 `type` 判定，不要求接口路径是标准的 `api.php/provide/vod`**——实测不少源用 `/inc/apijson_vod.php` 这类自定义路径 |
| `sites[]` 中类型缺失、但地址命中 Apple CMS 特征 | 宽容按 JSON 采集站处理（社区配置常漏写 `type`） |
| `lives[]` 中的普通播放列表 | `type:0` 或未声明类型的 `url`。**按内容嗅探格式**（M3U 或 TVBox txt 频道列表），不按扩展名判定 |
| `wallpaper` | 作为界面背景，加载失败静默忽略 |
| `parses[]` / `flags` | 会被解析并在设置面板中列出（解析线路名、走解析的线路白名单），供你了解这份配置提供什么 |
| `spider` | 会被识别（含 `;md5;` 校验值的拆分）并提示「本客户端不运行 jar」 |

### 两个容易踩的坑（已在实现里处理）

1. **`.txt` 不等于「不是 M3U」**。实测 `jinenge/tvbox` 的 `./lib/interface.txt` 内容就是标准 M3U；
   按扩展名拒绝会把一个完全可用的直播源误判为不支持。因此一律拉取后按**内容**嗅探。
2. **相对路径相对的是配置地址，不是本站页面**。配置里 `./lib/iptv.m3u`、`./jar/x.jar` 很常见，
   必须相对**配置 JSON 所在目录**解析——尤其是多仓配置，要相对**仓库地址**解析。

## 会被跳过（并在导入结果里说明数量与原因）

| 情形 | 原因 |
| --- | --- |
| `type:3` / `api: csp_xxx` / `jar` / `.js` / `.py` / `node:` | **Spider 站点**。jar 里是 Android DEX 字节码，需要 `DexClassLoader` 与 Android API；drpy 类 JS 需要 QuickJS + 宿主注入的 Java 能力。浏览器与 Node 都没有这些，**这是纯 JS 客户端的硬边界**，不是解析缺陷 |
| `type:0` 的 XML 接口 | 本项目只解析 Apple CMS 的 JSON 输出，不解析 `at/xml` 通道（需要 XML 解析器） |
| `lives[]` 的单仓 JSON（`group` + `channels`，或 `type:1` / `.json` 地址） | 需要 TVBOX 的聚合逻辑，未实现 |
| `sites[]` 中 `type:4` 的外链站点 | 需要站点自带的嗅探逻辑，未实现 |
| `parses[]` 中 `url` 为 `Parallel` / `Sequence` / `Web` / `Demo` | 这些是 TVBOX **客户端内置**的聚合解析器，不是可请求地址 |
| `searchable: 0` 的站点 | 本站的入口是聚合搜索，导入后无从使用 |

## 实测样本（说明「为什么有的配置几乎导入不出东西」）

| 配置 | 站点数 | 可用点播站点 | 直播源 | 结论 |
| --- | --- | --- | --- | --- |
| `jinenge/tvbox` 的 `tvbox.json` | 42 | **0**（42/42 全是 Spider：39 个 jar + 3 个 drpy JS） | **7**（全部可用，含一个内容实为 M3U 的 `.txt`） | 这份配置的可播放点播站点为 0；只有直播源能用。它还**没有 `parses` 字段**，所以解析功能也未启用 |
| 某社区配置（101 个站点） | 101 | **54**（`type:1` JSON 采集站） | 1（单仓 JSON，不支持） | 可导入一半以上；同时带 22 条解析线路与 10 个平台名 |

> 换句话说：**站点数量多 ≠ 能用**。先看 `sites[].type` 的分布，Spider 占比高的配置对本客户端基本无用。

## 已知缺口

按优先级排列，都是「可做但还没做」：

1. **分类浏览（进行中）**：TVBox 的浏览范式是「站点分类列表 → 分类 → 筛选 → 分页」。
   上游约定已核实：`?ac=list` 返回 `class[]`（分类）与 `filters`（筛选项），
   `?ac=videolist&t=<分类id>&pg=<n>` 取该分类分页列表。当前客户端只有聚合搜索 + 海报网格。
2. **解析线路：已支持「JSON 解析」类，浏览器嗅探类明确不支持**。

   播放页在配置里有可用解析线路时会出现一排「解析线路」按钮（内置聚合解析器不列）。
   点一下就用该线路把当前播放地址换成真实地址，成功后提示来自哪条线路，并可「恢复原地址」。

   - **请求形状（有配置证据）**：真实配置的解析地址**全部**写成 `…/player/?url=` 或 `…/?url=`，
     客户端把原始播放地址（**不编码**）直接接在后面。实测同一接口「拼接编码后地址」超时、
     「原始地址直接拼接」返回 200，所以这里按原始拼接实现；少数只给到路径的会补 `?url=`。
   - **响应形状（有源码证据）**：播放结果是 TVBOX 的 play-result JSON，字段表（`url` / `header` …）
     来自上游客户端源码；客户端只取 `url`（限 http(s)）与 `header`（防盗链）。
   - **能力边界**：`type:0` 的解析接口实测返回的是 **HTML 播放页**（`…/player/?url=`），
     它需要在浏览器里执行页面脚本并拦截真实媒体请求——**本客户端做不到**。
     这种情况会明确提示「这条解析线路返回的是播放页，本客户端无法运行」，
     **不是**当成「解析失败」，用户能分清「线路不适用」与「线路坏了」。
     Electron 端理论上可以用隐藏窗口 + `webRequest` 实现嗅探，但那是另一项独立功能。
   - **只能核到这一步**：`type:1` 的解析接口在本机全部不可达，其 JSON 契约无法实测；
     因此上线的行为是「按已知形状请求 + 严格校验结果 + 判不出来的如实说明」，不假装成功。
   - 安全：解析地址过字面量 + DNS 双校验；待解析地址只做字面量校验（我们不请求它，
     只是递给第三方服务，但不该把内网地址递出去）；响应体截断 512KB。
3. **`type:0` 的 XML 站点**：约占社区配置的一半，需要引入 XML 解析。
4. **遥控/键盘可达性不完整**：TVBox 是焦点驱动导航。目前海报卡有焦点态，
   但频道列表、抽屉、换源面板、历史面板的列表项还没有 `focus-visible` 描边。
5. **界面截图待重新生成**：`docs/preview/*.png` 仍是改造前（LibreTV 风格）的截图。

## 排查建议

- 用「设置 → TVBox 配置地址」导入后，面板会给出**站点形态统计**（JSON 采集站 / XML / Spider / 外链）
  与**跳过原因明细**；全是 Spider 时也会明确说明，而不是让你以为解析失败。
- 也可以直接打接口自查（服务端与桌面数据层都提供）：
  `GET /api/tvbox?url=<配置地址>` 返回完整配置视图与统计，不做裁剪。
- 配置里若带 `msg` 字段，TVBOX 客户端会**中止加载**（配置作者用它宣告接口失效）；
  本客户端同样会把它当作失效配置并在面板里提示。
- 配置是**多仓格式**（`{urls:[{name,url}]}`）时，会自动跟随第一个仓库的地址；
  仓库里还是多仓则明确报错，不做无限套娃。
